# Campus Explorer — scope notes

`campus-app.js` is Phase 1 of turning `campus.html` into a real digital
twin. What's actually implemented, and what isn't, so nobody (including
future-you) mistakes a placeholder for a finished feature.

## Real, working now
- Real Three.js addon pipeline via CDN ES modules: `GLTFLoader` + `DRACOLoader`,
  `EffectComposer` with `UnrealBloomPass` + `SSAOPass` (desktop only) +
  `OutputPass`, `OrbitControls`, `PointerLockControls`.
- 5 buildings, each a real `GLTFLoader.load("assets/models/<id>.glb", ...)`
  call with a procedural fallback on load failure — drop a real model at
  that path and it replaces the box automatically, no code change.
- Click a building → cinematic tween-to-focus, highlight pulse, info panel.
- AI Guide text box: a small alias matcher for navigation ("take me to the
  library") plus the *real* `HKBKChat` engine and `HKBK_KB` for everything
  else — same knowledge base and retrieval logic as the main site's chat
  widget, not a separate/fake one.
- Day/night lighting cycle (sun/rim/ambient/window-emissive lerp).
- Orbit camera + a basic Walk mode (pointer-lock WASD, flat ground, no
  collision — see limitation below).
- Instanced trees, boundary wall, road ring, one parking lot, building name
  label sprites (toggleable).

## Explicitly not built yet
- **Real building models.** Nothing has been 3D-scanned or modeled; every
  building is a labelled glass/concrete box. This is the single biggest gap
  between this and an actual "digital twin."
- **Interior exploration.** No interiors exist — walking into a building
  currently just walks through its wall.
- **Weather** (rain/fog/wind/clouds), the **1997→2026 timeline**, and
  **analytics heatmaps** — none of these have real data behind them yet, so
  building them now would mean inventing numbers. Wire them to real
  admissions/placement data first.
- **IoT / CCTV layers** — there is no such data source for this site. Not
  planned unless one exists.
- **Collision detection** in Walk mode — you can currently walk through
  buildings and the boundary wall.
- **LOD** (`THREE.LOD`) — buildings are single fixed-detail meshes; only the
  tree count and SSAO are tier-adjusted for mobile/tablet right now.

## Adding a real model
Export a `.glb` (Draco-compressed if you want smaller files) named after a
building's `id` in `BUILDINGS` (see `campus-app.js`) and place it at
`assets/models/<id>.glb`, e.g. `assets/models/library.glb`. No other change
needed — the loader already looks there first.

## Milestone 1 — lighting & camera (added)

### Image-based lighting
`assets/hdr/campus-sky.hdr` is loaded with `RGBELoader`, run through
`PMREMGenerator` and set as `scene.environment`. It is **vendored, not
fetched from a CDN** — the addon modules still come from jsDelivr, but no
*asset* does.

The HDRI itself is generated by `tools/make-hdri.py`: an analytic
Preetham-style sky with a real high-dynamic-range sun disc (peak radiance
~425), warm horizon haze and a bounce-lit ground hemisphere. It is a
genuine 32-bit radiance file, so PBR materials behave correctly.

**It is not a photograph.** There are no clouds, no skyline, no ground
detail, so reflections read as clean studio sky rather than a real
Bengaluru afternoon. Dropping a captured or downloaded `.hdr` in at the
same path is a no-code-change upgrade and is the recommended step before
any publication or demo that claims photorealism.

`AmbientLight` was removed entirely — a uniform ambient term lifts shadows
flatly and destroys form, and is one of the most reliable visual tells of
an unlit-looking WebGL scene. The directional light was dropped from 2.2 to
1.35 since the environment now carries most of the illumination, and its
position is matched to the sun direction baked into the HDRI (azimuth 58°,
elevation 34°) so highlights and shadows agree.

### Contact shadows
A shared radial-gradient decal is multiply-blended under each building
footprint. PCF softening throws away exactly the tight occlusion at the
base of a wall, which is what makes shadow-mapped buildings look like they
hover.

### Cinematic intro
A 15-second scripted move on load: ~90 m altitude, slow glide, a bank
through the turn, diagonal descent to a held frame on the main block, then
handover to the orbit controls. Position and look-at are separate
Catmull-Rom curves so the camera can lead its subject. Tone-mapping
exposure opens from 0.12 as the environment map finishes decoding, so the
"sunlight reveals the campus" beat never lands on unlit materials.

Skippable by any pointer/key/wheel input or the skip button. The HUD and
guide panel stay hidden until handover.

**Not implemented from the requested storyboard:** ambient audio (wind,
birds). Browsers block autoplaying audio without a user gesture, so it
would either fail silently or require a click-to-start prompt in front of
the sequence, which defeats the purpose.

### Idle breathing
A sub-decimetre positional drift after 2.5 s of no input, ramped in over
2 s. The offset is removed before `orbit.update()` and re-applied after —
OrbitControls derives its spherical state from `camera.position` each
frame, so an offset left in place is read back as user rotation and the
camera slowly wanders.

### Hover response
Throttled to one raycast per frame; illumination lift and label emphasis
are smoothed exponentially rather than snapping, plus a pointer cursor.

### Bug fixed while doing this
The focus-highlight loop did `emissiveIntensity += pulse` every frame with
no restore, so intensity ratcheted upward for as long as the page was open
and highlighted buildings eventually blew out to white. Base values are now
cached per material and written absolutely.

### Still the biggest gap
None of the above changes the fact that the buildings are **boxes**. Good
lighting on placeholder geometry is well-lit placeholder geometry. One
properly modelled main block (correct proportions, real mullions, baked AO)
would do more for perceived quality than everything in this section
combined.

## Semantic Cinematic Director (SCD)

`director.js` — the component that decides *how* to frame a target, given
*why* the user asked.

Before: every query produced the same generic fly-to. Now the same building
presents differently depending on intent — "where is the main block" gets
the entrance at approach height on a 46° lens; "what does the main block
look like" gets a low three-quarter detail frame on a compressed 34° lens;
"show me the campus" gets a high wide 55° establishing frame.

### Why it's a separate file with no imports
`director.js` imports nothing, and knows nothing about Three.js, meshes,
materials or the DOM. It consumes plain metadata (bounds, world position,
entrance heading) and returns plain numbers (position, target, fov,
duration, easing name). Three consequences:

1. It is unit-testable in Node with no browser and no WebGL —
   `node tests/director-test.js`, 37 assertions.
2. Replacing a procedural box with a real `.glb` requires **no changes
   here**: every shot is expressed relative to the bounding box, and
   `setBoundsFromObject()` refreshes the metadata from the loaded model,
   so all shots re-solve themselves.
3. It is reusable for a campus that isn't HKBK's — point it at different
   metadata.

### Intents and shots
Shots are keyed by *intent*, not camera name. `navigation`, `architecture`,
`orientation`, `facilities`, `administrative`, each with a fallback chain.
A building with no `entranceHeading` skips the entrance shot rather than
confidently framing a blank wall, and the substitution is reported.

### Explainability
Every decision carries intent, confidence, selected shot, lens, composition
note and a human-readable reason, surfaced in the info panel. The camera
makes a choice on the user's behalf; showing the reasoning is what makes it
auditable — and it's what the evaluation study asks participants to judge.

### Honest limitations
- **Intent classification is rule-based**, not learned and not an LLM: a
  scored keyword/pattern matcher with a directive-phrase bonus so "where
  is the admissions office" resolves to navigation rather than
  administrative. Transparent and cheap; fails predictably. **Do not
  describe it as language understanding.** The reported confidence is a
  pattern-match score, not a calibrated probability.
- **`entranceHeading` values in the registry are placeholders**, chosen to
  face the internal road. They are not surveyed and must be corrected
  against the real campus layout before any evaluation study.
- **Shots are tuned against boxes.** Framing that reads well on a 7.5×3.4
  placeholder will need re-tuning once a real model exists. Expressing
  shots parametrically limits the damage; it doesn't eliminate it.

### Control condition for evaluation
`genericFlyTo()` is retained — it is exactly the pre-Director behaviour, so
a study can compare semantic-directed framing against generic fly-to
directly rather than against a remembered baseline.

## Conversational Spatial Memory (CSM)

`scene-context.js` — grounds follow-up questions in whatever is currently
on screen, so "how many books are there" resolves to the library without
the user re-naming it.

**What it is NOT:** no embeddings, no vector store, no LLM context window,
no long-term memory, nothing persisted. It is five fields describing the
scene (`currentBuilding`, `previousBuilding`, `lastShot`, `lastIntent`,
`timestamp`) plus a resolver mapping deictic words onto them. The retrieval
engine's existing 10-turn buffer handles *topical* follow-ups; this handles
*spatial* ones, which that buffer cannot because it has no idea where the
camera is.

Like `director.js`, it imports nothing and touches no Three.js or DOM type
— `node tests/scene-context-test.js`, 51 assertions.

### What it resolves
- **Self** — "how many books are there", "is it open", "take me inside",
  and bare part-references like "where is the entrance" or "show me the
  roof", which only mean anything relative to something in view.
- **Relational** — "what's nearby", "how far is the main block": returns
  ranked neighbours with distance and compass bearing, highlights them,
  and moves no camera.
- **Back** — "go back" returns to the previously visited building.

Explicit building matching always wins; grounding is attempted only when
the query names no building.

### Fails closed, on purpose
When a reference is used but cannot be grounded — no building visited yet,
or context older than the 5-minute TTL — it says so instead of silently
assuming the most recent target. A confidently wrong grounding is worse
than an admitted miss, and in a user study it would be indistinguishable
from a retrieval error.

### Honest limitations
- **Pattern-based, not coreference resolution.** A fixed list of deictic
  and pronominal forms. It will not resolve "the one with the glass front"
  or "the building I asked about before last". Do not describe it as
  anaphora resolution.
- **Distances are in world units, not metres.** The campus model is not
  surveyed, so `describeNearby()` deliberately says "units". Do not
  present these as real distances until the layout is measured.
- **Compass bearings assume +z is north**, matching the Director's heading
  convention. That convention is internal, not tied to real-world north.

## Street View walkthrough — real photos, not the 3D model

`street-view.html` / `js/3d/campus/street-view.js` / `css/street-view.css`.

The 3D scene above is a parametric blockout — accurate proportions, no
photographic detail (see the honest-limitations sections throughout this
file). Sometimes what's wanted is not that; it's the actual building.
This is a second, much simpler page for that: a real-photo sequence
walkthrough, gate to Main Block, built from **125 JPEG frames sampled
directly from the walkthrough video** (`video/video/`, not the 3D model,
not a render). No Three.js, no WebGL, no canvas — a fixed image sequence
with forward/back navigation, click-ahead like Street View's chevrons,
swipe on touch, arrow keys on desktop.

**Route (`assets/tour-photos/manifest.json`), four chapters from four
separate clips in walking order:**

| Chapter | Frames | Source clip | Duration sampled |
|---|---|---|---|
| At the gate | 1–7 | IMG_0204 (1 frame) + IMG_0205 | 0.9s + 9.1s |
| Walking onto campus | 8–15 | IMG_0201 | 13.5s |
| Approaching the Main Block | 16–25 | IMG_0196 | 19.5s |
| Around the Main Block | 26–125 | IMG_0192 | 133.5s |

125 frames, 1440px wide, 15.5 MB total.

**What this is not, stated plainly because the interaction looks like real
Street View and it would be easy to assume it works the same way:**

- **Not one continuous shot.** Four separate clips placed in walking order.
  There is a hard cut at each chapter boundary — the camera does not
  smoothly continue between clips, because they were filmed separately.
- **Not panoramic.** The source is ordinary narrow-field phone video, not a
  360° camera, so there is no drag-to-look-around at a fixed point. Forward
  and back along the path only.
- **Not distance-uniform.** Frames are sampled at a fixed *time* interval
  per clip, not a fixed *distance* — a slow-walked stretch yields more
  steps than a fast one. Step count is not a proxy for how far you moved.
- **Not the same path as the 3D scene's gate.** `IMG_0192`, the bulk of the
  route, actually starts at the Main Block's own entrance steps and walks
  outward through campus — it does not begin at the boom-gate footage
  (`IMG_0204`/`IMG_0205`) it is chained after. The chapters are a curated,
  honest-about-being-curated route, not a single unbroken walk from the
  physical gate to the physical building.
- **People appear in these photos.** Unlike the 3D model, this feature
  shows the source footage as-is, including students and staff walking
  through frame. Nothing is generated or altered.

Re-run `tools/make-main-block.py`'s neighbour — there is no regeneration
script for this feature yet; the frames in `assets/tour-photos/` are a
one-time extraction. Re-extracting (different clips, denser sampling, a
real gate-to-building continuous shot if that footage is ever captured)
is the natural next step, not currently automated.

## Digital Twin production — main block asset

### `assets/models/main-block.glb`
The placeholder box for `main-block` is now replaced by a real GLB. It
loads automatically through the existing `GLTFLoader` path; no code change
was needed for the swap itself.

**What it is: an architectural blockout, generated parametrically by
`tools/make-main-block.py`, not a Blender model and not a scan.** No
Blender is available in this environment. Geometry was originally derived
from measurements *estimated off two campus photographs*
(`hero-modern-block.jpg`, `glass-facade-angular.jpg`); it has since been
**rebuilt against a walkthrough video of the actual building** — see the
next section for what that changed and what it did not.

**Not reproduced:** exact dimensions (proportions are close, absolute
metres are *not* survey-accurate), signage, the "I love HKBK"
installation, the adjacent older grey block, any interior, and photographic
surface detail. It reads as clean architectural massing, not as photoreal
concrete.

1,644 triangles, 1.0 MB, 13 named meshes, 11 named materials. Of that
total, **863 KB is the embedded texture maps and 122 KB is geometry**.
Draco is not applied — the loader supports it, but it compresses the 122 KB
half only, and that would save nothing worth the decode step.

A properly modelled and textured replacement at the same path remains the
single highest-value upgrade to this project. This is a credible stand-in
for demonstration, not a substitute for that.

### Rebuilt from walkthrough video
The two photographs got several things wrong, and a walkthrough video of
the building (39 clips in `video/video/`) settled most of them. Clips were
triaged one frame each; **eight show the Main Block exterior and fed the
rebuild — IMG_0192 (a 2m15s walk past the whole complex), IMG_0195–0198
and IMG_0200–0202.** The other 31 are hostel, bus bay, approach drive,
interiors, corridors, the older render-and-arch teaching blocks, the degree
college and the gate; they were discarded. 35 frames plus targeted zoom and
contrast crops were reviewed.

**What the video showed, and what changed as a result:**

| | Photo-derived model | Video |
|---|---|---|
| Glass volume | 18 × 15 × 19 m slab beside a longer wing | A **compact, near-cubic tower**. IMG_0202 is the most orthographic frame available and gives width : total height ≈ 0.90 — slightly taller than wide. Now 20.5 × 19 × 22.6 m. |
| Plan cant | Canted 7° in plan | **Flat front face.** The reflected skyline runs unbroken across it; no frame supports a cant. `GLASS_YAW` is now 0. |
| Entrance canopy | Separate cantilevered slab projecting 3 m | **There is no canopy.** The glazed mass oversails a recessed ground floor; what photographs read as a canopy is the slab edge, flush with the facade above. Modelled as a fascia band, and the lobby is set back 2.2 m behind the facade plane. |
| Steps | 3 | **5**, banded granite, inside the recess. |
| Fin screen | Ran the full height from 0.3 m | **Starts at the first-floor slab.** The wing's ground floor is plain render with a projecting entrance portal. |
| Roofline | Two centred setbacks | **One step, at one end** — a lift/stair overrun about a storey above the parapet. Seen from opposite sides in IMG_0202 and IMG_0192, which is the cross-check that makes it trustworthy. |
| Storeys | 5 at 3.8 m on both volumes | **6 on the tower, 5 on the wing**; the wing stands about a storey and a half shorter. The wing's five are *counted directly* — one arched window register per floor behind the fins. The tower's six are *inferred*: 9–10 spandrel bands divided by the panels-per-storey the assumed floor height implies. Weaker evidence, and the table should be read that way. |

**What the video did *not* show, and is therefore unchanged:**

- **The plan angle between the two volumes.** In IMG_0196 and IMG_0192 the
  fin wing is strongly foreshortened, suggesting an L wrapping the
  forecourt; in IMG_0201 it reads near-parallel to the tower. The angle is
  not measurable from this footage, and it is the one change that would
  swing the bounding box wildly. **The two volumes are left side by side
  as before rather than encoding a guess.** This is the largest remaining
  known inaccuracy in the model.
- **Absolute scale.** Handheld video with no reference length does not give
  it. Four independent anchors in these clips — parked scooters, cars, a
  seated figure, and the curtain-wall panel module — disagreed by more than
  3×, because foreground and facade sit at very different depths. Every
  metre figure here is **scaled from an assumed 3.6 m floor-to-floor** with
  a taller ground floor, applied to the counted storeys. Storey *counts*
  are observed; storey *heights* are assumed. Do not present the metres as
  measured.
- **The fin wing's length**, cut off or tree-blocked in every frame. It
  keeps its previous photo-derived 34 m.

**No people from the video appear in the output.** Several clips have
students walking through them; they are scale reference only. The generator
emits parametric boxes and contains no photogrammetry path — this is a
proportion and shape reference, not a reconstruction.

**Still not visually verified.** Geometry, scale, origin, axis, material
names, UV coverage and the bounding box are checked programmatically; how
it *looks* is not, because no headless WebGL is available here.

### The campus is now in metres
**This was a real bug, found when the model landed.** The scene was
authored in arbitrary units — `main-block` was 7.5 wide on a 20-unit
campus. The real model is 55 m wide, which would have appeared roughly
seven times too large for its surroundings.

The whole scene was converted to metres (factor 7.35, preserving the
existing relative layout): building positions and sizes, campus radius,
road and boundary geometry, tree scale and scatter, fog distances, shadow
camera frustum, light positions, orbit limits, the cinematic intro path,
and the control-condition fly-to. Walk-mode eye height (1.7) was already
correct and is unchanged.

Building sizes *other than* the main block remain estimates scaled from
the original placeholder values. They are not measured.

### Director shots retuned
Shots are relative, so they re-solved themselves — but two of them
re-solved badly. Keying an entrance shot off the footprint diagonal parked
the camera 110 m back from a 55 m-wide building, and the doors became
invisible.

`extentMode` was added to the shot definitions: `"envelope"` (default,
footprint diagonal — right for wide shots) or `"local"` (max of height and
depth — keeps close shots close on a long building). Entrance, detail and
approach shots use `local`; overview, context and arrival use `envelope`.
Elevations and distances were retuned to match.

All 37 Director assertions still pass — the change is additive and
`extentMode` defaults to the previous behaviour.

#### Re-checked after the video rebuild — and *not* retuned

The rebuild moved the bounding box from **55.2 × 21.8 × 20.3 m** to
**57.7 × 27.1 × 21.0 m**: barely wider, a fifth taller. That is enough to
move every camera, so each shot was re-solved by hand against both boxes
before deciding whether to touch the `SHOTS` table.

| Shot | Distance old → new | Camera height old → new | Frame fill old → new |
|---|---|---|---|
| Entrance | 49 → 61 m | 13 → 17 m | 1.91 → 1.91 |
| Detail | 39 → 49 m | 18 → 23 m | 1.10 → 1.10 |
| Approach | 51 → 64 m | 17 → 21 m | 1.90 → 1.90 |
| Context | 125 → 132 m | 46 → 51 m | 2.36 → 2.39 |
| Arrival | 119 → 126 m | 40 → 43 m | 1.89 → 1.92 |
| Overview | 161 → 169 m | 82 → 89 m | 2.84 → 2.87 |

"Frame fill" is the vertical extent the lens covers at that distance
divided by the extent the shot keys off — the number that decides whether a
shot still *contains* its subject. **It drifts by at most 0.03, about 1%.**
The cameras moved further out because the building got bigger, which is the
behaviour the relative shot definitions exist to produce.

**So no `distance` or `elevation` value was changed.** The shots re-solved
themselves correctly, which is the design working rather than an
observation that needed acting on.

**What that check does not cover.** Frame fill answers "does the building
fit", not "can you see the doors" — and the doors are the entire point of
the entrance shot, which is why `extentMode: "local"` was introduced in the
first place. The entrance camera moved from 49 m to 61 m, and the lobby is
now **recessed 2.2 m behind the facade plane**, which it was not when these
shots were last tuned. Whether the lobby still reads at that distance
cannot be established from the bounding box; it needs a rendered frame.
**It is therefore listed with the other visually unverified items below,
not claimed as fine.** If it turns out to misframe, `distance` on the
`entrance` shot is the one value to change — the Director's tests use
synthetic fixtures and do not pin it.

### Landscape
Kerbs either side of the ring road, painted parking bay markings, a
footpath from the road to the entrance, lawn strips matching the
photographs, and 24 instanced lamp posts (12 on mobile) whose heads share
the buildings' day/night emissive curve. Positions are plausible, **not
surveyed**.

### Not done in this phase
- **No automated verification that any of this renders correctly.** No
  headless WebGL is available here. The geometry, scale, origin, material
  names and bounding box are verified programmatically; how it *looks* is
  not. Open the page and check before demonstrating it.
- **Specifically unverified: whether the entrance shot still reads.** The
  lobby is now recessed 2.2 m and the camera solves 12 m further back than
  when the shot was tuned. Frame fill is unchanged, so the building is
  contained — but that does not establish that the doors are visible, which
  is what the shot is for. Ask "where is the main block" on `campus.html`
  and look. If the doors are lost, lower `distance` on the `entrance` shot
  in `director.js`; nothing else needs to move.
- No LOD, no texture compression, no interiors, no collision.
- Materials have no maps. That is the next visual bottleneck.

## Procedural PBR material maps

`tools/make-materials.py` generates `assets/textures/` — the map set that
replaces flat PBR values on the main block and on the scene's ground, road
and paths.

| Map | Contents |
|---|---|
| `concrete_albedo.png` | tonal drift, aggregate speckle, vertical water streaking |
| `concrete_normal.png` | pitting, aggregate relief, form-board seams |
| `concrete_orm.png` | R = ambient occlusion, G = roughness, B = metalness |
| `glass_normal.png` | subtle per-panel bow — curtain-wall glass is never optically flat, and the wobble in the reflection is most of what reads as glass rather than mirror |
| `glass_orm.png` | smudging, dirtier panel edges, sealant lines |

876 KB total at 512², embedded in the GLB (now 1.0 MB).

**Why this mattered:** uniformity is the most reliable tell that a surface
is CG. Real concrete varies in tone and roughness across a wall, darkens
where water runs, and is darker in corners. None of that needs an artist —
it is noise, and noise is computable.

### Implementation notes
- **UVs are world-space planar**, projected on the two axes each face
  normal is not dominant in, divided by a per-part tile size. Tiling
  therefore runs continuously across adjacent boxes — a fin and the wall
  behind it share the same grain rather than each restarting at its own
  seam. Fins and steps use a tighter tile (1.6 m, 1.8 m) so the grain is
  not blown up on a 130 mm section.
- **All maps tile.** Noise is generated on a wrapped lattice and gradients
  use `np.roll`, so there are no visible edges at the repeat.
- **`baseColorFactor` divides out the map's mean** rather than being
  flattened to white. Otherwise the dark plinth, the steps and the pale
  fins would all collapse to whatever mid-grey the shared texture happens
  to be. Each surface keeps its intended value *and* gains the variation.
- **Mullions and the canopy are deliberately untextured** — thin metal
  sections never seen close enough for a map to register.
- The scene's ground, ring road and footpath load the same concrete maps
  at different repeat rates, and fall back to flat colour if the files are
  missing.

### Honest limitations
These are **procedural approximations, not scanned material data.** They
carry no photographic detail: no real aggregate, no real staining pattern,
no weathering corresponding to how this building actually ages. They make
surfaces read as plausibly non-uniform, not as photographically correct.

A scanned set from Poly Haven or AmbientCG would be better and is a
drop-in replacement at the same paths. That, and a properly modelled
building, remain the two upgrades that need a human.

**Still not visually verified.** No headless WebGL here — texture
generation, UV coverage, embedding, sampler wrap mode and material
assignment are all verified programmatically. How it looks is not.
